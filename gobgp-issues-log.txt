BUG LOG: GoBGP v4.8.0 + FastNetMon flowspec integration issues

HOST: netmon (10.102.41.201)
ASN: 201251
BGP peers: 10.101.2.21, 10.101.2.22 (Juniper MX, iBGP)
GoBGP version: v4.8.0
FastNetMon builds: custom fork at github.com/Hostzero-GmbH/fastnetmon

=== ISSUE 1: gRPC service name mismatch ===

FastNetMon's gobgp_client was compiled against GoBGP v2 protobufs
(package apipb, service apipb.GobgpApi). GoBGP v4.8.0 serves
api.GoBgpService, not apipb.GobgpApi.

Error in log:
  AddPath request to BGP daemon failed with code: 12 message
  unknown service apipb.GobgpApi

Fix (committed):
  - Replaced gobgp.proto and attribute.proto with GoBGP v4.8.0 versions
  - Added v4 proto files: capability.proto, common.proto, extcom.proto, nlri.proto
  - Updated stubs: namespace apipb:: -> api::, service GobgpApi -> GoBgpService
  - Updated enum: TableType::GLOBAL -> TableType::TABLE_TYPE_GLOBAL

=== ISSUE 2: Linker error, abseil ordering ===

After cmake reconfigure, fastnetmon_api_client fails to link:
  libgpr.so: undefined reference to absl::debian9::Mutex::lock
  libabsl_synchronization.so: DSO missing from command line

Root cause: LINK_WITH_ABSL block was placed BEFORE gRPC library links.
GNU ld bfd resolves left-to-right, so gpr's absl dependency is not
satisfied when absl appears first.

Fix (committed):
  - Moved LINK_WITH_ABSL block after gRPC and protobuf library links
  - absl::synchronization now appears after libgpr.so on link line

=== ISSUE 3: Both RTBH unicast and flowspec fire simultaneously ===

fastnetmon_logic.cpp lines 1382-1400:
  Code path 1 (line 1382): unconditional gobgp_ban_manage() for unicast RTBH
  Code path 2 (line 1392): gobgp_flow_spec_ban_manage() if ban_action != BLACKHOLE

Both code paths ran independently when gobgp=on. The unicast RTBH path had
no check for ban_action, so even with ban_action=flow_spec_discard, the
unicast /32 route was still sent.

Fix (committed):
  - Unicast RTBH path now only fires when ban_action == BAN_ACTION_BLACKHOLE
  - Flowspec path fires for all other ban_action values

=== ISSUE 4: Global ban_action config key ===

ban_action is read from config key prefix + "ban_action" where prefix is
the host group name plus underscore, or empty for global.

To set flowspec globally (not per host group):
  ban_action = flow_spec_discard

Without this, global ban_action defaults to blackhole.

=== ISSUE 5: BGP session cycling with code 3/10 ===

Symptom: BGP session establishes, GoBGP sends UPDATE, Juniper MX sends
NOTIFICATION code 3 subcode 10 (invalid network field), session drops,
GoBGP reconnects, repeats.

The UPDATE GoBGP sends (confirmed via tcpdump):
  MP_REACH_NLRI (type 14):
    AFI: 1 (IPv4), SAFI: 133 (flowspec)
    Next hop length: 0
    NLRI: 00 01 20 (3 bytes)
  Extended Community:
    Type: 0x8006 (traffic-rate)
    Value: 0 (rate-limit zero = discard)

Hex dump of UPDATE payload:
  0001 8500 0001 20 c0 1008 8006 0000 0000 0000

The NLRI 00 01 20 is invalid. Valid flowspec NLRI should be:
  01 20 D1 83 76 04  (type 1 = destination prefix, /32, IP bytes)

The 0x00 type byte is not a valid flowspec component type (RFC 5575
types start at 1). This suggests either:

  a) GoBGP v4.8.0 auto-generates a malformed flowspec route on session
     establishment when ipv4-flowspec AFI/SAFI is configured for a neighbor
  b) The export policy (fnm-flowspec) causes GoBGP to generate a default
     route with invalid NLRI
  c) A stale/corrupted flowspec route was stored in GoBGP's internal state
     from the old (proto-mismatch) AddPath calls

Attempted fixes that did NOT resolve:
  - gobgp neighbor reset
  - systemctl restart gobgpd
  - Adding FLOWSPEC-VALIDATE import policy on MX side

Next step: comment out export-policy-list to test if the UPDATE is
generated by GoBGP's policy evaluation rather than a stored route.
